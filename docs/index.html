RepoPilot 코드 해설서

이 HTML 하나로 RepoPilot 전체를 이해하기

이 문서는 RepoPilot의 폴더 구조, API 흐름, 백엔드 서비스, agent node, 정적 분석 규칙, patch 검증, 프론트엔드 상태 관리, 무료 배포 방식까지 한 번에 이해하도록 만든 독립형 코드 가이드입니다.

1. 이 프로젝트가 하는 일

RepoPilot은 public GitHub 저장소를 입력받아 코드를 임시로 clone하고, 분석 가능한 파일을 인덱싱한 뒤, local static rule과 간단한 retrieval을 이용해 evidence 기반 finding과 patch draft를 보여주는 무료 웹 데모입니다.

무료 우선

OpenAI, Claude, 유료 inference API, Qdrant Cloud, hosted DB 없이 동작합니다.

No paid API CPU Basic

근거 우선

finding에는 파일 경로와 line range가 붙습니다. 주장만 던지는 구조를 피합니다.

Evidence File/Line

작은 MVP

LLM으로 깊게 추론하는 제품이 아니라, 무료 환경에서 agent 구조를 보여주는 현실적인 MVP입니다.

Static Rules Scoped Demo
핵심 문장: RepoPilot은 “자동으로 모든 버그를 고치는 AI”가 아니라, “코드를 가져오고, 근거를 찾고, 정적 분석 finding과 patch draft를 보여주는 무료 agent 구조”입니다.

2. 전체 구조 한눈에 보기

프로젝트는 크게 apps/api와 apps/web으로 나뉩니다. 백엔드는 clone, indexing, analysis, patch validation을 담당하고, 프론트엔드는 사용자가 그 흐름을 조작할 수 있는 대시보드를 제공합니다.

영역 경로 역할
API 앱 apps/api/app/main.py FastAPI 앱 생성, 서비스 등록, API router 연결, static frontend 서빙
API routes apps/api/app/api/routes repo import, index, analysis, chat, patch, GitHub PR mock endpoint
서비스 계층 apps/api/app/services repo clone, indexing, analysis 실행, patch 검증 같은 실제 작업 단위
코드 분석 apps/api/app/code 언어 판별, Python/JS/TS parsing, 무료 정적 분석 rule
Retrieval apps/api/app/rag 코드 chunk 생성과 in-memory 검색
Agent apps/api/app/agents planner, repo reader, code searcher, analyzer, bug detector 등 node workflow
Frontend apps/web Next.js UI, form, dashboard, diff viewer, API client
Deploy Dockerfile Next.js static export를 만들고 FastAPI 컨테이너에서 함께 서빙

전체 데이터 흐름

1. URL 입력
사용자가 GitHub URL과 branch를 입력하고 Import & Index를 누릅니다.
2. RepoService
URL을 검증하고, repo id를 만들고, 임시 workspace에 저장소를 clone합니다.
3. IndexingService
분석 가능한 파일만 걸러서 parser와 chunker에 넘깁니다.
4. Retriever
코드 chunk를 repo id별로 메모리에 저장하고, task query와 맞는 chunk를 검색합니다.
5. Agent
여러 node를 순서대로 실행해 summary, timeline, finding을 만듭니다.
6. PatchService
선택된 evidence path를 기준으로 patch draft를 만들고, 승인된 파일만 건드렸는지 확인합니다.

3. 사용자가 버튼을 누르면 실제로 무슨 일이 생기나

apps/web/app/page.tsx Frontend Orchestrator

이 파일은 화면의 중심입니다. React state로 현재 repo, analysis 결과, patch 결과, 선택된 task, deep analysis 여부, loading/error 상태를 들고 있습니다. 

const [repo, setRepo] = useState<RepoImportResponse | null>(null);
const [analysis, setAnalysis] = useState<AnalysisResponse | null>(null);
const [patch, setPatch] = useState<PatchResponse | null>(null);
const [task, setTask] = useState<AnalysisTask>("overview");

handleImport()는 먼저 /repos/import를 호출하고, 이어서 /repos/{repo_id}/index를 호출합니다. 즉 사용자가 한 번 누르지만 내부적으로는 “가져오기”와 “인덱싱”이 연속 실행됩니다. 

const imported = await importRepo(url, branch);
await indexRepo(imported.repo_id);
setRepo(imported);

handleAnalysis()는 선택된 task를 /analyses로 보내고, 결과를 AnalysisDashboard에 넘깁니다.

handlePatch()는 첫 번째 finding의 첫 번째 evidence path를 승인된 파일로 보고 patch를 생성합니다. 그래서 현재 MVP에서는 patch가 “선택한 evidence 파일 범위 안에서만” 만들어지는 구조입니다.

apps/web/lib/api.ts API Client

frontend가 backend와 통신하는 함수들이 모여 있습니다. 배포 환경에서는 FastAPI와 정적 frontend가 같은 origin에서 뜨기 때문에 기본 API base는 빈 문자열입니다. 

const API_BASE = process.env.NEXT_PUBLIC_API_BASE_URL ?? "";

로컬 개발에서 Next dev server와 FastAPI server를 분리해서 쓸 때만 NEXT_PUBLIC_API_BASE_URL을 줄 수 있습니다.

4. 백엔드 코드 해설

apps/api/app/main.py FastAPI Entry

create_app()은 RepoPilot 백엔드 전체를 조립하는 함수입니다. 여기에서 settings를 읽고, retriever를 만들고, LLM provider를 만들고, agent를 만들고, 여러 service를 app.state.services에 등록합니다. 

retriever = LocalQdrantLikeStore()
llm = build_llm_provider(settings.llm_provider)
agent = RepoPilotAgent(llm=llm)

이름은 LocalQdrantLikeStore지만 현재는 실제 Qdrant가 아닙니다. “나중에 Qdrant로 바꿀 수 있는 모양”을 가진 in-memory store입니다. 

app.state.services = {
  "repo_service": RepoService(...),
  "indexing_service": IndexingService(...),
  "retriever": retriever,
  "analysis_service": AnalysisService(...),
  "patch_service": PatchService(),
  "github_service": GitHubService(),
}

mount_frontend()는 Hugging Face 배포에서 중요합니다. Next.js static export 결과인 apps/web/out/index.html이 있으면 FastAPI가 frontend 파일까지 같이 서빙합니다.

apps/api/app/api/deps.py Dependency Helper

route 함수들은 직접 service를 import해서 새로 만들지 않습니다. 대신 request.app.state.services에서 이미 만들어진 service dict를 받아옵니다. 이 덕분에 retriever와 agent 상태를 앱 전체에서 공유할 수 있습니다. 

def services(request: Request) -> dict:
    return request.app.state.services

API route별 역할

Endpoint 파일 하는 일
POST /repos/import routes/repos.py GitHub URL을 검증하고 public repo를 clone합니다. clone 실패 시 offline demo README를 만듭니다.
POST /repos/{repo_id}/index routes/repos.py workspace 파일을 돌며 parser, chunker, retriever 저장까지 실행합니다.
POST /analyses routes/analyses.py task에 맞는 chunk를 검색하고 agent workflow를 실행합니다.
POST /chat routes/chat.py 질문과 관련된 chunk를 찾아 evidence와 함께 간단한 답변을 반환합니다.
POST /patches routes/patches.py patch draft를 만들고, 승인된 파일 범위를 벗어나지 않았는지 검증합니다.
POST /github/pr routes/github.py 현재는 실제 PR 생성이 아니라 confirmation이 필요한 mock workflow입니다.

5. Agent workflow 해설

현재 agent는 LangGraph 라이브러리를 직접 쓰지는 않습니다. 대신 LangGraph처럼 state를 들고 node들을 순서대로 실행하는 구조입니다. 그래서 나중에 실제 LangGraph로 바꿀 때도 개념상 이동이 쉽습니다.

apps/api/app/agents/state.py Shared State

모든 node는 같은 AgentState를 받고, 필요한 내용을 추가한 뒤 다시 state를 반환합니다. 이 state 안에는 repo id, task, 검색된 code chunk, finding, timeline, summary가 들어 있습니다. 

@dataclass
class AgentState:
    repo_id: str
    task: str
    retrieved_chunks: list[dict]
    findings: list[Finding] = field(default_factory=list)
    timeline: list[AgentStep] = field(default_factory=list)
    summary: str = ""
apps/api/app/agents/graph.py Workflow Runner

RepoPilotAgent는 node 목록을 고정된 순서로 갖고 있습니다. run()이 호출되면 state를 만들고 node를 하나씩 실행합니다. 

self.nodes = [
    PlannerNode(llm),
    RepoReaderNode(llm),
    CodeSearcherNode(llm),
    ArchitectureAnalyzerNode(llm),
    BugDetectorNode(llm),
    TestWriterNode(llm),
    PatchWriterNode(llm),
    ReviewerNode(llm),
]

현재 node들은 대부분 timeline을 채우고, ArchitectureAnalyzerNode와 BugDetectorNode가 finding을 만듭니다.

Node별 설명

Node 현재 역할 결과
PlannerNode 선택된 task에 대한 분석 계획을 timeline에 기록합니다. timeline step
RepoReaderNode 검색된 chunk들이 어떤 파일에서 왔는지 요약합니다. timeline step
CodeSearcherNode 몇 개의 chunk가 line metadata와 함께 검색됐는지 기록합니다. timeline step
ArchitectureAnalyzerNode 첫 번째 evidence chunk를 기반으로 기본 summary finding을 만듭니다. summary + info finding
BugDetectorNode bug_scan 또는 patch_generation task일 때 static rule을 실행합니다. rule finding
TestWriterNode 현재는 test generation이 준비됐는지 timeline에만 기록합니다. timeline step
PatchWriterNode patch generation은 사용자 승인 action이 필요하다고 timeline에 기록합니다. timeline step
ReviewerNode finding이 file/line evidence를 갖는지 확인했다는 review step을 남깁니다. timeline step

6. 코드 분석과 retrieval

apps/api/app/services/repo_service.py Clone Safety

RepoService는 public HTTPS GitHub URL만 허용합니다. SSH URL, 다른 domain, path traversal을 막습니다. 

^https://github\.com/(?P<owner>...)/(?P<name>...)

repo id는 clone_url + branch를 SHA1 hash로 줄여서 만듭니다. 그래서 같은 repo와 branch는 같은 workspace id를 갖습니다.

Hugging Face 무료 환경에서는 clone이 오래 걸리면 안 되기 때문에 clone_timeout_seconds가 들어가 있습니다.

apps/api/app/services/indexing_service.py Indexing

IndexingService는 repo 내부 파일을 순회하면서 분석 가능한 파일만 고릅니다. 무거운 directory와 너무 큰 파일은 건너뜁니다. 

IGNORED_DIRS = {
    ".git", "node_modules", ".next", "dist", "build",
    "__pycache__", ".venv", "venv",
}

허용 확장자는 .py, .ts, .tsx, .js, .jsx, .md입니다. Space 환경에서는 env로 file count와 file size를 제한합니다.

apps/api/app/code/parser.py Parser

Python은 표준 라이브러리 ast로 parsing합니다. class, function, async function, import를 찾습니다.

JS/TS는 아직 tree-sitter가 아니라 regex 기반입니다. 그래서 정확한 compiler 수준 parsing이 아니라 “MVP용 lightweight 추출”입니다.

주의: README에서 “tree-sitter 완료”라고 말하면 틀립니다. 현재는 Python AST + JS/TS regex scaffold가 정확한 표현입니다.
apps/api/app/rag/chunker.py Chunking

CodeChunker는 파일 내용을 일정 line 수 단위로 자릅니다. 각 chunk에는 path, start line, end line, content가 들어갑니다. 

CodeChunk(
    path=document.path,
    start_line=start + 1,
    end_line=start + len(selected),
    content="\n".join(selected),
)
apps/api/app/rag/retriever.py In-memory Search

현재 retrieval은 vector DB가 아닙니다. query에서 단어를 뽑고, chunk의 path와 content에 그 단어가 몇 개 들어있는지로 단순 점수를 매깁니다. 

query_terms = set(re.findall(r"[A-Za-z_][A-Za-z0-9_]*", query.lower()))
matches = sum(1 for term in query_terms if term in haystack)

이 방식은 무료이고 빠르지만 semantic search는 아닙니다. 그래서 현재 README에는 “in-memory chunk search”라고 표현하는 것이 맞습니다.

apps/api/app/code/rules.py Static Rules

RepoPilot이 현재 실제로 bug candidate를 찾는 핵심 파일입니다. LLM을 부르지 않고, 각 line에 대해 deterministic rule을 실행합니다.

Rule 감지 조건 Severity
Hardcoded secret candidate password, secret, token, api_key 같은 이름에 문자열 literal 할당 high
Bare except hides failures except: 단독 사용 medium
Dynamic eval execution eval(...) 호출 high

finding을 만들 때는 반드시 Evidence(path, start_line, end_line)를 같이 넣습니다. 이게 RepoPilot의 evidence-first 구조입니다.

7. patch 생성과 검증

apps/api/app/services/patch_service.py Patch Boundary

현재 patch는 진짜 source code를 분석해 정교하게 수정하는 단계는 아닙니다. 승인된 evidence path를 target으로 삼아 unified diff 형태의 draft를 만듭니다. 

target = approved_paths[0] if approved_paths else "README.md"

중요한 부분은 validate()입니다. diff 안에서 실제로 건드리는 path를 추출하고, 그 path가 approved_paths 안에 있는지 확인합니다. 

if path not in allowed_paths:
    messages.append(f"{path} is outside approved scope.")
왜 중요한가? AI agent가 마음대로 여러 파일을 고치는 것을 막기 위한 human-in-the-loop 경계입니다. 현재는 단순하지만 “승인된 파일만 수정”이라는 안전 구조를 보여줍니다.
apps/api/app/services/github_service.py Mock PR

현재 GitHub PR 생성은 mock입니다. confirmed가 false면 blocked를 반환하고, true면 demo URL 형태를 반환합니다.

따라서 README에 “실제 PR 생성 가능”이라고 쓰면 틀립니다. “PR workflow boundary가 있고 실제 PR은 다음 단계”가 정확한 설명입니다.

9. 무료 배포 구조

Dockerfile Hugging Face Spaces

Dockerfile은 multi-stage build입니다. 첫 번째 stage는 Node.js로 Next.js frontend를 static export합니다. 두 번째 stage는 Python runtime으로 FastAPI를 실행합니다. 

FROM node:20-slim AS web-build
RUN npm ci
RUN npm run build

FROM python:3.12-slim AS runtime
COPY apps/api ./apps/api
COPY --from=web-build /app/apps/web/out ./apps/web/out

Hugging Face Spaces는 기본 app port로 7860을 기대합니다. 그래서 Dockerfile도 uvicorn을 7860으로 실행합니다. 

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "7860"]

무료 배포에서 돈이 안 드는 이유

  • LLM API를 호출하지 않습니다.
  • GPU를 쓰지 않습니다.
  • hosted database를 쓰지 않습니다.
  • Qdrant Cloud 같은 외부 vector DB를 쓰지 않습니다.
  • Hugging Face Spaces CPU Basic에서 실행합니다.
운영 한계: 무료 Space는 sleep, CPU, disk, network 제한이 있습니다. 따라서 작은 public repo를 분석하는 데모에 맞춰져 있습니다.

11. 현재 한계와 다음 작업

현재 한계

  • LLM 추론이 아니라 static rule 기반입니다.
  • JS/TS parsing은 regex scaffold입니다.
  • retrieval은 vector search가 아니라 단어 match입니다.
  • patch는 실제 고품질 코드 수정이 아니라 draft입니다.
  • GitHub PR은 mock boundary입니다.

다음에 하면 좋은 일

  • tree-sitter로 parser 교체
  • 정적 분석 rule set 확장
  • dependency graph 기반 위험 탐지
  • patch template 품질 개선
  • demo repo benchmark 추가
면접에서 설명할 포인트: “무료 배포 조건 때문에 cloud LLM 없이 동작하는 구조를 먼저 만들었고, repo ingestion, indexing, retrieval, evidence-first finding, patch scope validation, static frontend serving까지 end-to-end로 구성했습니다.”
